## 1. 本轮范围与不做什么

### 1.1 范围（U2 四项，逐项单独验收）

| 项 | 交付 | 为什么是现在做 |
|---|---|---|
| **A. 同主机多 shell** | 一个 SSH 连接上开多个 shell channel，各自独立标签/回放/尺寸 | U1 留下的最硬的结构债：`connId` 同时充当 profile id、runtime id 与 viewer 绑定键（§2.1），不做身份分层就永远只能"一主机一 shell" |
| **B. SFTP** | 浏览 / 上传 / 下载 / 重命名 / 新建目录 / 删除 / 传输队列 | 工作区规划 §6 已把它列为"次版"，且 ssh2 原生能力齐备（§2.4），不需要新依赖 |
| **C. 工作区记忆** | 标签集合与激活项、rail 宽度/折叠、专注模式、每主机最近 SFTP 路径 | 目前只记 `fontSize` 等零散偏好（§2.5），刷新后标签全丢 |
| **D. 精确终端恢复** | 全屏 TUI（vim/top）在"刷新 / 重开浮层"后屏幕与光标原样 | **价值已被 D0–D4 大幅收窄**（§4.4）：常驻 iframe 已让"切走切回"零损失，只剩刷新场景 |

### 1.2 不做什么（明确排除，避免把首版拖成大平台）

- **不做**服务器仪表盘（CPU/内存/延迟）：无可靠数据源，规划 §6 已排除。
- **不做**远程 DSH / 多用户 / 跨设备共享终端：需另做认证与 TLS（规划 §8 末条）。
- **不做**跳板机、端口转发、SSH config 导入：那些是 U3，且需独立安全评审。
- **不做**本机文件系统读写：SFTP 的上传/下载**只走浏览器 ↔ HTTP ↔ 远端**，host 端不碰本机磁盘（§4.2.3 的核心安全决策）。
- **不引入**前端框架：继续原生 DOM + xterm（规划 §9 末条）。

## 2. 现状取证（代码事实，非推断）

### 2.1 身份模型：profile 与 runtime 共用 `connId`

`lib/runtime.js:52` —— `this.conns = new Map() // connId -> RuntimeConn`。也就是说：

- **profile id**（`store.js` 里持久化的连接记录）＝ **runtime id**（一次 SSH 连接实例）＝ **viewer 绑定键**（`ws.sshRc`）。
- `RuntimeConn`（`lib/runtime.js:387`）**一个连接只有一个 shell**：`this.stream = null`（`runtime.js:391`），由 `onReady()` 里的 `rc.client.shell({...})`（`runtime.js:236`）创建，`stream.on('close')` 时直接 `rc.dispose()`（`runtime.js:248-255`）—— **shell 结束 = 连接结束**。
- scrollback 环挂在**连接**上：`rc.sbChunks / rc.sbLen`（`runtime.js:405-406`），`push()` 写它（`runtime.js:412-436`）。
- 尺寸是**连接级单值**：`rc.cols / rc.rows`（`runtime.js:393-394`），`viewerResize` 直接改它（`runtime.js:319-327`）⇒ 多 viewer 会互相覆盖（规划 §5.3 已点名"最后一个 resize 获胜"）。

> **结论**：多 shell 不是"多几个标签按钮"，而是**身份分层**问题 —— 与规划 §5.1 的判断一致。任何绕过分层的做法（例如给同一 stream 开多个 xterm）都会立刻撞上回放、尺寸与输入归属三个坑。

### 2.2 WS 协议与输入归属（今天是清楚的）

`index.js:195-218` 的 `/ssh/ws` 只认四帧：

| 帧 | 载荷 | 语义 |
|---|---|---|
| `attach` | `{ connId, cols, rows }` | 附着到该连接（`runtime.attach`，`runtime.js:265`） |
| `input` | `{ data }` | 写进**该 ws 绑定的** rc 的 stream（`viewerInput`，`runtime.js:314`） |
| `resize` | `{ cols, rows }` | 改该 rc 的尺寸并 `setWindow` 进真实 PTY（`viewerResize`） |
| `detach` | — | 解绑（`runtime.detach`，`runtime.js:329`） |

输入/尺寸**按 `ws.sshRc` 绑定路由**而非 connId 查表（U0 的成果），被替换代次的僵尸 viewer 会收到 `STALE_VIEWER` 并被关闭（`runtime.js:300-312`）。**这条纪律必须在多 shell 下升级为按 `(rc, shell)` 绑定**，否则多标签会互相打字。

围栏在 upgrade 阶段做（`index.js:242-249`，`fenceCheck`），HTTP 与 WS 同源三道围栏。

### 2.3 scrollback 与内存预算

- 每连接一个 256KiB 环（`cordis.patch.yml` 的 `scrollbackBytes: 262144`）。
- `push()` 里对慢 viewer 有背压淘汰：`ws.bufferedAmount > 8MiB` 即 1011 关闭（`runtime.js:22, 427-431`）。
- **多 shell 若不设总预算，N 个 shell = N × 256KiB**（10 个标签即 2.5MiB/连接，且回放是 `Buffer.concat` 全量拼接）。§4.1.4 给出按连接的总预算方案。

### 2.4 SFTP 能力（ssh2 1.17.0，随包 `SFTP.md` 实测）

本地 `node_modules/.pnpm/ssh2@1.17.0/node_modules/ssh2/SFTP.md`（21KB）确认可用方法：

- 传输：`fastGet` / `fastPut`（并行读写）、`createReadStream` / `createWriteStream`（流式）
- 列目录：`readdir(path | handle)` 支持 `opendir` + 多次 `readdir` 分页（`list` 为 `false` 表示读完）
- 变更：`rename` / `unlink` / `mkdir` / `rmdir` / `stat` / `lstat` / `realpath` / `readlink` / `symlink` / `chmod` / `chown` / `utimes`
- 打开方式与属性：`OPEN_MODE` / `stringToFlags` / `_ATTRS_`

> ⇒ **不需要新增依赖**（规划 §9 末条"新增依赖须单独核验"本轮不触发）。`SFTPWrapper` 由 `client.sftp()` 在同一 ssh2 Client 上创建，与 shell channel 并存（§9 SPIKE S-U2-2 要实测这一点）。

### 2.5 前端状态与偏好落点

`app.js` 的 `state`（顶层常量）：

> ⇒ 工作区记忆的落点选择在 §4.3 给出：**偏好进 `localStorage`（跨标签页共享），工作区快照进 `sessionStorage`（按标签页隔离）**。

## 3. 架构：三层身份 + 附着票据

### 3.1 三层身份

```
connId（profile，持久，store.js）
  └─ runtimeId（一次 SSH 连接实例 = 一个 ssh2 Client；含 generation 语义）
       ├─ shellId #1（一个 shell channel：stream + 尺寸 + 回放环 + viewer 集合）
       ├─ shellId #2
       └─ sftp（惰性创建的 SFTPWrapper，连接级共享）
```

- **同主机仍限一运行连接**（规划 §6 既有约束）：`SshRuntime` 维护 `byProfile: Map<connId, runtimeId>`，多 shell 是同一 runtime 下的多个 shell，**不是**多个 SSH 连接。
- `connId` 继续是 profile 的对外名字（路由/REST 不变）；`runtimeId` 是**新的内部标识**（`rc-<uuid>`），前端只见 runtimeId 与其下的 shellId。

### 3.2 附着票据（规划 §8 的硬要求）

> 规划 §8 原文：**"在增加多 viewer / 同主机多 shell 前引入短期附着凭证、运行实例归属与写入/尺寸权限。不得把运行连接 ID 本身当作授权证明。"**

设计（复用本线已有的成熟模式 —— 指纹确认 token 就是"随机一次性 + generation 绑定"）：

| 属性 | 取值 |
|---|---|
| 获取 | `POST /ssh/api/attach`（带 `connId`）→ `{ ticket, runtimeId, shells: [{shellId, title, state}], expiresAt }` |
| 形式 | `randomUUID()`，**一次性**，TTL **30s**（只够建立 WS，不够复用） |
| 绑定 | `ticket → { runtimeId, connId, generation, mode: 'write' \| 'read' }` |
| 消费 | WS `attach { ticket, cols, rows }`；消费即作废；过期/重放 → `TICKET_INVALID` 并关闭 |
| 权限 | **写入所有权（已定，2026-09-15）**：一个 shell 同一时刻只有一个 `write` viewer（primary），其余为 `read`；显式「接管」按钮可换手，原 owner 立即转只读并收到 `write.revoked`（规划 §5.3：不能"最后一个 resize 获胜"） |
| 失效 | runtime teardown / shell 关闭 / generation 替换 ⇒ 该 runtime 的所有票据作废（与 `expirePendingFor` 同构） |

> 这一步是 U2 的**安全前置**，必须在多 shell 与 SFTP 之前落地：否则 runtimeId 一旦暴露给前端就成为事实上的授权凭证。

### 3.3 兼容性策略

WS 协议**不做双栈**：前端与 host 同版本发布、iframe 与宿主同源，双栈只会长期留两套代码。改为：

- 帧里带 `v: 2`；host 收到无 `v` 的旧帧直接拒绝并让前端**重载页面**（提示"插件已升级，请刷新"）。
- `runtimeId` 与 `shellId` 都在 REST/WS 里显式传递，**不存在"用 connId 猜 runtimeId"的兜底路径**（兜底就是绕过分层）。

## 4. 分项设计

### 4.1 A. 同主机多 shell

#### 4.1.1 运行时模型

`lib/runtime.js` 拆分：

| 现 | 后 |
|---|---|
| `SshRuntime.conns: Map<connId, RuntimeConn>` | `conns: Map<runtimeId, RuntimeConn>` + `byProfile: Map<connId, runtimeId>` |
| `RuntimeConn.stream`（唯一 shell） | `RuntimeConn.shells: Map<shellId, ShellChannel>` |
| `rc.sbChunks / sbLen`（连接级回放环） | `ShellChannel.sbChunks / sbLen`（**每 shell 独立**） |
| `rc.cols / rows`（连接级尺寸） | `ShellChannel.cols / rows` |
| `rc.sockets: Set<ws>` | `ShellChannel.viewers: Set<ws>`（`ws` 上绑定 `shellId` 而非 `rc`） |
| `rc.stream.on('close') → rc.dispose()` | `shell.on('close') → 仅关闭该 shell`（连接保持，除非最后一个 shell 也结束） |

`ShellChannel` 字段：`{ id, stream, cols, rows, sbChunks, sbLen, title, createdAt, viewers: Set<ws>, writeOwner: ws|null }`。

#### 4.1.2 协议扩展

| 帧 | 载荷 | 说明 |
|---|---|---|
| `attach` | `{ v:2, ticket, cols, rows }` | 消费票据；服务端回 `ready { runtimeId, shells: [...] }` |
| `shell.open` | `{ cols, rows, cwd? }` | 新建 shell（`client.shell({ term, cols, rows })`）；回 `shell.opened { shellId, title }` |
| `shell.close` | `{ shellId }` | 关闭该 channel（**不等于断开 SSH**） |
| `input` | `{ shellId, data }` | 仍走 viewer 绑定校验：`ws.shellId === frame.shellId && ws.mode === 'write'` |
| `resize` | `{ shellId, cols, rows }` | 同上；非 owner 的 resize 被拒绝（不再"最后一个获胜"） |
| `shell.takeover` | `{ shellId }` | 显式接管写入权（原 owner 收到 `write.revoked` 并转只读） |

帧尺寸上限沿用 256KB（`MAX_WS_FRAME_BYTES`），输入仍是字符串。

#### 4.1.3 前端模型

- `state.tabs` 由 `string[]`（connId）改为 `[{ key, connId, shellId, title, live }]`，`key = `${connId}:${shellId}``。
- 每标签一个 viewer（`session.js` 的实例）；切标签沿用现有"销毁-重挂 + host 侧回放"路径（**多 shell 后每 shell 有自己的环，回放天然隔离**）。
- 标签标题：默认 `label`，同主机多 shell 时追加 `#2 / #3`；支持双击重命名（仅前端，不落盘）。
- 新建 shell 入口：标签栏 `+`（下拉"新 shell" / "恢复上次布局"）。**不自动**在连接时开第二个 shell。

#### 4.1.4 内存总预算（必须，否则标签一多就爆）

- **每连接总回放预算**：默认 `1MiB`（可配 `scrollbackBytesPerRuntime`），在 shell 间**按创建顺序先到先得**：新 shell 加入时若总量超预算，从**最久未查看**的 shell 环头部裁剪（而不是拒绝新建）。
- 每 shell 仍有自己的上限（默认 `256KiB`），二者取小。
- 背压淘汰（`bufferedAmount > 8MiB`）改为按 shell 判定，不影响同连接其他 shell。
- 文档与 UI 明示：**回放不是完整历史**（规划 §5.4），裁剪会发生。

#### 4.1.5 边界与不做

- 同一 runtime 下 shell 数上限 **8**（已定，2026-09-15；超出拒绝并给出可读提示）—— 防"标签风暴"与 fd 泄漏。
- shell 结束（远端 `exit`）**不自动**关标签：标签保留并显示"会话已结束"，用户可"重新开一个 shell"（同一 runtime）或关闭标签。
- 不做 shell 分组/树形标签（首版平铺即可）。

### 4.2 B. SFTP

#### 4.2.1 通道选型（三选一，取 B）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 复用 `/ssh/ws` 发 SFTP 帧 | 复用围栏与票据 | 二进制流与 JSON 控制帧混用；大文件与背压难做；256KB 帧上限要改 | ✗ |
| **B. REST + 流式 HTTP** | 大文件天然流式；浏览器原生下载（`Content-Disposition`）与 `<input type=file>` 上传；可加 Range/断点；列表可缓存 | 需要让票据同时适用于 HTTP | **✓ 采用** |
| C. 独立 WS 端点 `/ssh/sftp` | 隔离清晰 | 仍要自研流控；浏览器下载体验差（要自己 Blob 落盘） | ✗ |

#### 4.2.2 REST 设计（全部挂在既有 `/ssh/api` 前缀下，围栏自动生效）

| 方法 | 路径 | 语义 |
|---|---|---|
| `GET` | `/ssh/api/sftp/list?ticket=&path=` | 列目录：`{ path, realPath, entries: [{ name, type, size, mtime, mode, isSymlink }], truncated }` |
| `GET` | `/ssh/api/sftp/download?ticket=&path=` | 流式下载（`createReadStream` → `res`，`Content-Length` 由 `stat` 提供） |
| `POST` | `/ssh/api/sftp/upload?ticket=&path=&size=&overwrite=0\|1` | 流式上传（`req` → `createWriteStream`） |
| `POST` | `/ssh/api/sftp/op` | 变更：`{ ticket, op: 'mkdir'\|'rename'\|'unlink'\|'rmdir', path, to? }` |
| `GET` | `/ssh/api/sftp/stat?ticket=&path=` | 单条元信息（覆盖/删除前确认用） |

- 票据复用 §3.2：`GET /ssh/api/attach` 之外再加一种 `scope: 'sftp'` 的票据（同一签发器，TTL 拉长到 **10 分钟**用于长传输，且**可续期**：`POST /ssh/api/sftp/renew`）。
- **上传大小上限** **512MiB**（已定，2026-09-15；`Content-Length` 预检 + 流式计数双重校验），下载不限但记字节数。

#### 4.2.3 安全边界（本轮最重要的设计决策）

1. **host 端不读写本机文件系统**。上传 = 浏览器 `File` → HTTP body → `createWriteStream(remote)`；下载 = `createReadStream(remote)` → HTTP → 浏览器落盘（由浏览器的下载策略决定位置）。⇒ 完全规避"远程内容写入本机任意路径"这一类风险，也不需要 host 端临时目录与清理。
2. **远程路径规范化**：每个操作前先 `realpath()`（不存在则 `realpath(dirname) + basename`），再校验：
   - 拒绝含 `NUL` / 换行 / 回车；
   - 长度上限 4096；
   - 规范化结果**不得**出现 `..` 段（`realpath` 之后仍含 `..` 视为异常）；
   - **不做 chroot**：用户对远端本就有全权（SSH 已给），沙箱根只会制造"看起来安全"的假象 —— 但 UI 必须始终显示**规范化后的绝对路径**，并在删除/覆盖时二次确认。
3. **覆盖与删除**：`unlink` / `rmdir` / 覆盖上传前先 `stat` 探测存在性，前端弹确认（含大小与 mtime）；目录删除仅允许空目录（`rmdir` 语义），**不做递归删除**。
4. **符号链接**：默认**只读不跟随**（`lstat` 区分 `isSymlink`），下载/上传遇到符号链接给出明确选择（"跟随到目标"需显式确认）；重命名符号链接改的是链接本身。
5. **并发与超时**：上传/下载各限 **2** 并发（队列串行化），单次传输空闲超时 60s；超出并发进队列而非拒绝。
6. **审计**：传输事件（`{ ts, op, path, bytes, ok, error }`）进**内存环形日志**（上限 200 条，不落盘、不记内容），供状态栏/面板查看；规划 §8"不自动把终端输出落盘"同样适用于文件内容。

#### 4.2.4 UI：文件抽屉

- 形态：终端右侧**按需打开**的抽屉（与既有 sheet 同一套视觉语言，但不遮终端；窄容器下降级为全屏 sheet）。
- 顶部：**面包屑**（每段可点）+ 路径输入（支持粘贴绝对路径）+ "上级/刷新"；
- 列表：名称 / 大小 / mtime / 类型图标；排序（名称/大小/时间）；`truncated` 时提示"仅显示前 N 项"；
- 操作：双击目录进入、双击文件下载、右键菜单（下载 / 重命名 / 删除 / 复制路径 / 新建目录 / 上传到此）；
- 上传：`<input type=file multiple>` + **拖拽到抽屉**（`DataTransfer`）两种入口；
- **传输队列**：底部固定条，逐项显示方向/文件名/进度/速度/取消；完成后可"清除已结束"；
- 与终端联动（可选，列为 U2.2 之后的增强）：终端里选中的路径/`ls` 输出中的文件名 → 右键"在文件面板中打开"。

#### 4.2.5 与 Agent 化的交叉

A1 的 `ssh_exec` 与未来的 `ssh_read_file` 会共享同一 runtime。SFTP 的**路径规范化函数必须是同一个**（抽到 `lib/paths.js` 或 `lib/runtime.js` 导出），否则两条通道的安全口径会漂移。列为 §10 待决策项。

### 4.3 C. 工作区记忆

#### 4.3.1 存什么 / 不存什么

| 存 | 不存 |
|---|---|
| 标签集合 `[{connId, shellSeq, title}]` 与激活项 | 终端输出 / 回放内容 |
| rail 宽度、折叠、专注模式、字号 | 密码 / 口令 / 私钥路径以外的任何凭据 |
| 每主机的最近 SFTP 路径（按 connId 记） | 指纹与信任状态（那是 host 侧事实） |
| 抽屉开关状态（sftp 打开与否） | 传输队列（不跨会话续传） |

#### 4.3.2 存哪（关键决策）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| `localStorage` 一张据 | 实现最简 | **多标签页互相踩**（两个窗口共享同一份"当前工作区"）；且会让"新开一个标签页"意外继承别人的现场 | ✗（仅继续存**偏好**） |
| **拆两张据**：偏好 → `localStorage`；工作区快照 → `sessionStorage` | 偏好跨标签页共享（符合"用户偏好"语义）；工作区按标签页隔离（符合"这块屏幕的现场"语义）；刷新保留、关标签页即忘 | 需要两个 key 与各自的迁移 | **✓ 采用（2026-09-15 用户拍板）** |
| host 侧 `workspace.json` | 跨浏览器/跨壳共享 | 新增一个写盘面与一套迁移/清理；与规划 §8"前端可存非敏感布局偏好"相悖 | ✗（留待将来"跨设备"需求再议） |

- key：`dsh-ssh:prefs`（v2，增 `railWidth`）与 `dsh-ssh:workspace`（v1，sessionStorage）。
- 两者都带 `version` 字段与**失败降级**：解析失败/版本不认 ⇒ 丢弃并回默认，**绝不因记忆数据损坏而白屏**（无痕模式下 `sessionStorage` 可能抛错，全部 `try/catch`）。
- 迁移：`prefs` v1 → v2 只补默认值，不需要破坏性变更。

#### 4.3.3 恢复语义（必须说清"恢复的是什么"）

- **恢复标签形状，不恢复连接**：刷新后标签按记忆重建为"未连接"态；用户点标签 → 走既有 `attach` 路径；**host 侧连接若仍存活则无损回到终端**（U0/U1 契约不变），若已结束则显示"会话已结束"。
- 恢复**不自动建立 SSH 连接**、不自动输入任何凭据 —— 与规划 §5.2"重新连接必须显式发起"一致。
- 恢复失败（例如 connId 已被删除）⇒ 该标签静默丢弃并在状态栏提示一条"有 N 个标签无法恢复"。

### 4.4 D. 精确终端恢复（价值收窄后的设计）

#### 4.4.1 为什么它不再是高优先项

D0 的实测已经证明：**浮层形态下 iframe 常驻、关闭只是 `visibility:hidden`**，因此

- 切到画布/对话再切回、关闭浮层再打开 ⇒ **iframe 从未重载，屏幕原样**（D2 验收 B2 项：30 次开关零损失、单 shell、零 resize 帧）；
- 真正会丢失屏幕的场景只剩两个：**页面刷新/reload**（D2 验收 B1a：浮层开着刷新会自动重开，但 iframe 重载 ⇒ 靠 host 侧 256KiB 回放重建，全屏 TUI 不保证原样）与**换浏览器/换机器**。

⇒ U2 把它降为**最后一项、且允许不做**（"spike 后若无兼容实现则记为已知边界"）。

#### 4.4.2 两条候选路线

| 路线 | 做法 | 前置 |
|---|---|---|
| **A. xterm 序列化** | `@xterm/addon-serialize` 把 buffer 序列化成 ANSI，前端在 reload 后回放该串（配合 host 侧一段"快照帧"） | SPIKE S-U2-3：稳定版 0.14.0 能否配 xterm 6.0.0（元数据无 peer 声明，必须实测） |
| **B. 自研屏幕快照** | host 侧按行保存"最近 N 行 + 光标位置 + 属性"，刷新后重绘 | 成本高；对 TUI 的属性/滚动区仍需自己处理 |
| C. 不做 | 明示"刷新后不保证全屏 TUI 原样" | 已可接受（现状） |

#### 4.4.3 若做 A，验收判据

vim 打开一个有内容的文件 → 记下 `cursorX/cursorY` 与屏幕文本（`buffer.active` 前 N 行）→ 刷新页面 → 恢复后**逐行文本一致且光标位置一致**；`top` 同理（至少 3 次刷新稳定）。

## 7. 验收矩阵

### A. 多 shell

1. 同一主机开 3 个 shell：三者输出互不串台；各自 `cd`/`export` 互不影响；关闭 #2 后 #1/#3 继续工作。
2. 每个标签独立回放：切走再切回，各自屏幕原样（不互相污染）。
3. 一个 shell 里的 `vim` 不影响另一个 shell 的尺寸（每 shell 独立 `setWindow`，host 侧记录各自的 `window-change`）。
4. 写入所有权：两个 viewer 附着同一 shell 时，非 owner 输入被拒且 UI 明示"只读，点接管可写入"；接管后原 owner 立刻转为只读。
5. shell 数上限 8：第 9 个被拒且有可读提示。
6. 远端 `exit` ⇒ 该标签显示"会话已结束"，其他标签不受影响；可"重新开一个 shell"。

### B. SFTP

1. 浏览：进入目录、面包屑返回、路径输入跳转、排序；权限不足的目录给出可读错误。
2. 上传：单文件、多文件、拖拽；重名时确认；大小超限被拒且有提示；完成后远端 `ls -l` 可见且大小一致。
3. 下载：大文件（≥100MiB）不占 host 内存（观察 RSS 平稳）；文件名与内容正确。
4. 变更：新建目录、重命名、删除文件、删除空目录成功；删除非空目录被拒（无递归删除）。
5. 安全：`../../etc/passwd` 一类路径被拒；符号链接默认不跟随且 UI 标注；含 NUL/超长路径被拒；未带票据或票据过期 ⇒ 401/403。
6. host 端零本机 IO：验收期间检查 host 进程未在你指定的任何本机路径产生文件（含临时文件）。
7. 队列：并发上限 2 生效（第 3 个排队）；取消正在传输的项后远端无残留半文件（或明确提示"已留下部分文件"）。

### C. 工作区记忆

1. 开 3 个标签 + 折叠 rail + 专注模式 → 刷新 ⇒ 标签形状与布局恢复、**不发生任何自动连接**。
2. 关掉标签页再开 ⇒ 回到干净默认（sessionStorage 语义）。
3. 两个标签页同时开着 ⇒ 各自的标签集合互不影响；字号（localStorage）两边一致。
4. 手工写入损坏的 `workspace` 值 ⇒ 页面正常打开并回默认（不白屏）。
5. 记忆里的 connId 已被删除 ⇒ 该标签静默丢弃 + 一条提示。

### D. 兼容与回归

1. `verify-all ssh` 全绿（含新增约 40 例）。
2. U0/U1/D0–D4 的既有门槛不回归：三主题换肤、四档宽度、浮层零损失（30 次开关）、A0 文案、退出与焦点归还。
3. 旧客户端页面（未刷新）遇到新 host ⇒ 明确提示"插件已升级，请刷新"，不出现静默错乱。
4. `data-width-handle` / `conversation.view` 等已清理项**保持零残留**。

### 12.3 补做探针（`_refs/scripts-archive/ssh-u2-verify/`）—— 方案 §9 四项逐条回答

| 探针 | 判据与实测 | 结果 |
|---|---|---|
| **A：同 Client 多 shell + sftp 并存**（`probe-a-multishell.mjs`，真 ssh2 Client × 真假 sshd） | **P1** 同一 Client 连开 **4 个 shell channel**（channelIds [1,2,3,4]，全部 ready）；**P2** 四者各设不同尺寸 → 服务端按 channel 记录到**精确对应**的 `window-change`（132×33 / 140×35 / 148×37 / 156×39，4 个不同 channel）；**P3** 只往 ch2 写标记 → **只有 ch2 收到回显**；**P4** 服务端让 ch2 **退出** → ch2 关闭、其余 3 个继续 PONG（shell 结束 ≠ 连接结束）；**P5** ch4 注入 **32MiB** 期间 ch1 的 PING 往返 **稳定 20ms**（空载 21ms）；**P6** `client.sftp()` 与 4 个 shell **并存**，期间 shell 仍通 | ✅ **7/7** |

**结论（方案 §9 四问的答案）**：
- **S-U2-1（同 Client 多 shell channel）**：**可行**，且尺寸/输出/生命周期三者隔离精确；
- **S-U2-2（sftp 与 shell 并存 + 大流量影响）**：**可行**，32MiB 并发下同连接其他 channel 的 RTT **无可测退化**（本机回环，真实广域网的带宽竞争仍需 U2.2 用真实主机复验）；
- **S-U2-3（addon-serialize × xterm 6.0.0）**：**兼容**，普通缓冲区与 alt-screen 均 100% 保真 ⇒ §4.4 的方案 A 可用，U2.4 从"可选"升级为"有实现路径"（体积随 scrollback 线性增长，落地需配滚动上限或分区 serialize）；
