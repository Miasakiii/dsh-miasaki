4S4 — 精确终端恢复（3/3 场景 100% 保真）

实验方法：离线 xterm 6.0.0 双实例（headless Edge /d4/ 探针页），buffer 级 serialize/restore 语义复刻（逐 cell 提取字符/宽度/bold/inverse → 行级压缩 JSON → ANSI 重放恢复 → 逐 cell 保真度对比）。三个场景 + U0 字节回放基线对比。addon-serialize 因 npm 被 SIGKILL 未完整安装，本轮用内置 buffer API 复刻——结论等价（官方 addon 的 serialize 就是同一 buffer API 的优化封装）。

结论与建议：GO（带条件）——serialize/restore 是唯一能恢复 TUI 画面的路径（字节回放对 alt-screen 结构性无效），且保真度可达 100%。但数据量随 scrollback 线性增长（270 行 ≈ 622KB），U2 落地必须二选一：
方案 α：serialize 只保 viewport（30 行 ≈ 80KB）+ scrollback 仍走字节回放——TUI 精确恢复 + 历史近似恢复，数据量可控；
方案 β：全量 serialize——完全精确但需要压缩（gzip 前 622KB，且随使用增长）与更严格的存储限额。
建议 α：与 §5.4「普通日志可回看 + TUI 精确恢复」的分层语义对齐；安全边界（不含用户输入回放、不偷偷按键）在两种方案下都成立。

5S1 — SFTP 能力与基准（受阻待放行）

脚本 spike-s1-sftp.mjs 已交付（判据：单文件 ≥5MB/s 回环、并发 8 无交错、100×10KB 批传零错、readdir 1000 条 <1s、重命名原语）。执行在写临时目录文件时被安全护栏拦截（审批超时）。未执行——按台账记「受阻待放行」：需用户在安全护栏中放行「Node 脚本临时目录文件写入」类操作后重跑（一条命令：node spike-s1-sftp.mjs）。S1 不阻塞 S2/S3/S4 的结论。
