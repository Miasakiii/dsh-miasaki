一句话结论

U2 的自动化闸门全绿，但实机验收在「首次连接」这一步就被挡住：等待指纹确认时 viewer 已 attach 而那时没有任何 shell， 前端无条件发出的 input/resize 被 host 判为 STALE_SHELL，该错误横幅覆盖了唯一带「核对指纹」按钮的分支 ⇒ 新主机连不上。 顺着这条线还查出「连接就绪不补绑 viewer」（同为阻断）与「同主机多 shell 输入串台」（高危，正是方案 §8 风险表第一条）等共 4 处真实缺陷。 4 处已全部定位并修复；修复与 U2.4 的 addon 都需重启 dsh web 才生效 ⇒ 实机复验待重启。

四处缺陷：因果链与修复

U2-A · 阻断

首连的指纹确认入口被 STALE_SHELL 覆盖

等待指纹（无 shell）→ viewer 依 U0 契约已 attach → onResize/onData 无条件发帧（shellId=null）→ host currentShell() 判绑定失效 → STALE_SHELL → 前端 onStatus('error') 写成 frameState → 横幅被覆盖，renderBanner 的 waiting-fingerprint 分支（唯一带「核对指纹」按钮）不再渲染。

旁证：状态栏「指纹待确认」按钮 onclick 实为 trustListSheet()（打开信任记录列表，此刻为空）—— 确实无路可走。

修：未绑定 shell 时不发 input/resize；绑定后由新增 syncSize() 补发真实尺寸（U0 契约不丢）。
U2-B · 阻断

连接就绪时不补绑已 attach 的 viewer

onReady() 建好主 shell 后只 broadcast({type:'ready', state, runtimeId, shells}) —— 不带 shellId、也不做服务端绑定 ⇒ 等待指纹期间 attach 的 viewer 永远停在 shellId=null， 指纹确认通过后终端仍不可用。

实测：手动点一次标签重挂（shell 已存在、走全新 attach）才拿到绑定，终端随即有内容（43 行）。

修：onReady 遍历 rc.sockets，对未绑定者 bindShell() 并逐发带 shellId/mode 的 ready。
U2-C · 高危（方案 §8 风险表第一条）

同主机多 shell 输入串台

① app.js openHost() 用 tabs.find(t => t.connId === id) 找标签 —— 同主机多 shell 永远命中第一个， 激活第 2/3 个标签反而改写第一个标签的 shellSeq 并把 activeTab 指回 0。
② session.js 拿票据后无条件取「第一个 live shell」，覆盖了调用方传入的 shellSeq。

实测：三标签各发一个标记 ⇒ sshd inputChannels [1,1,1]，标签 2/3 屏幕显示的是 ch-1 的内容。

修：openHost 支持 tabIndex 精确定位（三个调用点同步）+ 按 shellSeq 精确匹配（无 seq 才回退）+ attach 返回补 shellSeq。
U2-D · 中危

恢复后标签错乱 / 点标签空白

U2-C 的连锁：刷新恢复出 ["… #3","… #2","… #3"]（缺 #1、#3 重复）、点标签屏幕空白、 关闭对话框缺「关闭此 shell（连接保留）」（其条件依赖被错置的 activeTab）。

修：随 U2-C 一并闭环（openHost 的 tabIndex 路径 + 挂载恢复传索引），待重启复验。
