## 1. 背景与目标

用户对现有「用量」Tab（`dsh-token-monitor` v0.3.3，`conversation.view` order 15）提出两条诉求：

1. **会话页归会话**：每个会话的用量页只统计**当前会话**的用量，统计方法与「轨迹」页一致
   —— 从当前会话自己的数据投影，不掺入其他会话、不掺入跨会话累计。
2. **总量收口到全局**：该精简的精简；统计总量的模块（热力图、使用趋势、使用分布、
   使用总量）统一放到左侧边栏**设置按钮旁新增的「用量统计」按钮**，点击进入
   **新页面或浮窗**，显示 DSH 的使用总量。

设计目标（按优先级）：

- G1：会话「用量」Tab 内**不存在任何跨会话数据**，口径清晰、页面短小；
- G2：全局总量统计有唯一入口（侧栏脚部「用量统计」），与「设置」并列但不混入设置语义；
- G3：现有账本数据（`usage-log.jsonl`，380 天）零迁移成本，历史统计不丢；
- G4：保持零新依赖（纯 React / 手写 SVG / CSS grid）、主题令牌化、与 DSH 升级兼容。

## 2. 现状盘点

### 2.1 数据三通道（host 半 `lib/index.js`）

| 通道 | 来源 | 会话范围 | 生命周期 | 现状用途 |
|---|---|---|---|---|
| 官方持久聚合 | `sessionProjections.snapshot`（tokenUsage / contextPressure / contextBreakdown / sessionStats）+ `tokenMeter.measure` | **单会话** | 全会话日志、跨重启 | 会话页各卡（与「轨迹」页同源） |
| 实时明细 | `llm/stream` 增量 + `tools/result` | 按 `sessionId` 键控 | 本进程启动起 | 按模型明细 / 工具徽章 |

### 2.2 现有 Tab 区块（client 半 `lib/client.js`）及去向判定

| 现区块 | 数据源 | 精简后的去向 |
|---|---|---|
| 总览五卡（累计 / 峰值 / 最长聊天 / 连续天数） | 账本 | **迁全局页** |
| Token 活动年热力图（日 / 周 / 累计） | 账本 heatmap | **迁全局页** |
| 时间范围（近 7/30 日）+ 每日趋势图 + 模型用量环形图 | 账本 trend | **迁全局页** |
| 上下文剩余 hero（剩余 % + 分段条） | 官方（本会话） | **保留**（会话页头牌） |
| 今日用量 · 全部会话 + 日限额 + 重置账本 | 账本 + 本地配置 | **迁全局页**（重置与限额设置一并迁走） |
| 统计卡组（模型输出 / 缓存读写 / 官方累计 / 轮次步数） | 官方（本会话） | **保留**（并入会话总览） |
| 性能小卡（TTFT / 解码 / 模型与工具耗时） | 官方（本会话） | **保留** |
| 按模型明细条形 + 工具调用徽章 | 实时 | **保留但按会话过滤**（见 2.3） |
| 三通道口径脚注 | — | 拆分：会话页只写会话口径，全局页写账本口径 |

### 2.3 现存的会话边界缺陷（本次一并修正）

- `buildSummary(sessionId)` 把 `live.calls` / `live.tools` **全量返回**（未按
  `sessionId` 过滤），会话页的按模型明细与工具徽章实际混入了**同进程其他会话**的
  数据——与「只统计当前会话」的目标直接冲突。重构后 host 按 `sessionId` 过滤后再下发。
- `summary` 载荷恒定携带 30 天账本趋势 + 总览统计 + 限额配置，会话页每 3 秒重复拉取
  与自身无关的全局数据。重构后拆分路由，会话页载荷显著变小。

相对「塞进某个会话 Tab」的结构性优势。

## 4. 会话「用量」Tab 精简设计

### 4.1 区块清单（自上而下）

1. **上下文剩余 hero**（保留原样）：大字号剩余 % + 全宽分段条（分母 = contextWindow，
   45/75/95 三档变色）+ 系统/工具/消息/未使用图例。本会话的"剩余视角"头牌。
2. **会话用量总览**（由原统计卡组重组）：本会话累计 Tokens（官方口径
   `tokenUsage` 四段 + `tokenMeter` 总口径）、输入 / 输出 / 缓存读 / 缓存写分项、
   轮次 / 步数、会话活跃时长（可选，见 §10 决策点 D4）。
3. **按模型明细**（保留）：实时采集、**仅当前会话**；四段条形（输入 / 输出 / 缓存读 /
   推理）+ 调用次数。
4. **工具调用**（保留）：本会话内工具 × 次数徽章。
5. **性能**（保留）：TTFT / 解码耗时 / 解码速度 / 模型耗时 / 工具耗时（官方）。
6. **口径脚注**（改写）：官方聚合覆盖本会话全程（含插件启用前历史、跨重启，与
   「轨迹」页同源）；按模型明细与工具计数为插件实时采集、仅本进程；**本页不含任何
   跨会话累计**。全局统计请见左侧边栏「用量统计」。

### 4.2 数据面（会话路由）

- 新路由 `GET /dsh-token-monitor/session?sessionId=…`：仅返回
  `{ sessionId, official, live(按会话过滤), sampledAt }`，3 秒轮询，载荷瘦身。
- 旧 `/summary` 不再承担会话页职责（其全局部分并入 `/global`，见 §6.1）。

### 4.3 明确的"删除项"

总览五卡、热力图、时间范围 + 趋势图、模型环形图、今日用量 · 全部会话、日限额设置、
重置账本按钮——全部从 Tab 移除（迁往全局浮窗）。Tab 保留现有
`:has(.tokmn-pane)` 列宽解耦 CSS 不动。

## 6. 全局用量统计页模块设计（浮窗内容）

顺序即用户点名的模块序：**总览 → 热力图 → 使用趋势 → 使用分布 → 使用总量**。

1. **头部**：标题「用量统计」+ 记账起止说明（"自 YYYY-MM-DD 起记录 · 保留 380 天"）
   + 关闭按钮。
2. **使用总量 · 总览卡组**（原总览五卡 + 活跃天数，ZCode 头部统计行同构）：
   累计 Token 数 / 单日峰值 / 活跃天数 / 最长聊天时长 / 当前连续天数 / 最长连续天数。
3. **热力图**（原「Token 活动」整块迁移）：年视图 52 周、周一对齐、月标签；
   每日 / 每周 / 累计三态；悬浮富提示（日期 + tokens + 轮消息）。
4. **使用趋势**（原「时间范围 + 每日趋势」迁移）：近 7 / 30 日切换；按模型多序列
   平滑曲线 + 图例显隐 + 悬浮十字明细；配色按 30 天总量排名分配。
5. **使用分布**：
   - **模型用量环形图**（原迁移）：中心范围总量 + 右侧模型列表；
   - **会话用量 Top N**（**新增**）：近 30 日按会话聚合排行（tokens + 轮消息 +
     占比条），数据由账本 `sessionId` 维度聚合（§6.1）；会话标题尽力解析
     （`sessions.get` 取标题，失败降级显示 sessionId 截断）；
   - （后续可选）按星期 / 时段分布——账本已有日期与时间戳，v1.1+ 再议。
6. **使用总量 · 今日与限额**（原「今日用量 · 全部会话」+ 日限额设置迁移）：
   今日累计大数字 + 输入 / 输出 / 缓存读 / 轮消息分项；日限额进度条（未设置可就地
   设置，K/M 单位；已设置可编辑 / 清除）；**「重置账本」按钮迁至此**（confirm
   确认后清空，热力图 / 趋势 / 占比即时归零重计）。
7. **口径脚注**：全局统计来自跨会话账本（`usage-log.jsonl`，380 天，自插件首次部署
   起累计、跨 host 重启持久；部署前的历史会话不在其中）；限额为本地自定义配置
   （DSH 无配额接口）。

## 12. v0.5.0 增补：会话活跃分布与会话身份折叠（2026-09-10）

### 12.1 起因（用户实测反馈）

「用量统计」浮窗里的会话排行**认不出是哪个会话**：整列是 `session-<uuid>` /
`<uuid>` 内部编号，只有少数当前活着的会话偶尔显示标题。

### 12.2 根因

1. 账本 `usage-log.jsonl` 按 `sessionId` 聚合，本身不含标题；
2. 旧实现唯一的标题来源是 `ctx.sessions.get(id)` —— 这是**内存 store**，只认
   当前活着的会话，已归档会话一律 `undefined` → 降级为截断 ID。
   实测账本 45 个会话里绝大多数属于第 2 类，于是"整列编号"。

### 12.3 方案：改从会话日志折叠身份

宿主 `ctx.sessionQuery` 正是干这个的（`Service` 目录实测确认）：

| 方法 | 用途 | 关键性质 |
|---|---|---|
| `readTitleSnapshots(ids[])` | 批量折叠标题 | **支持已持久化（非内存）会话**；按会话隔离失败；结果保持入参顺序 |
| 返回 `SessionTitleObservation` | `{ session: SessionHeader, title? }` | header 带 `cwd` / `createdAt` / `origin` / `agentPreset` / `parentSession` |

实测（临时 host 探针插件，10 个真实历史会话）：**10/10 拿到标题**，来源 `provider`
（如"桌面端突然全黑屏无法操作"）或 `fallback`（首条消息截断），并带回工作目录与
`origin=subagent`。**冷读耗时 2.8s / 10 会话（≈0.3s/会话）** —— 这个数字决定了
下面的缓存与预热是必需项，不是优化项。

实现要点（`lib/index.js`）：

- **TTL 缓存**：有标题 30 分钟、无标题（日志尚无 title 事件）2 分钟重试；
  命中即零成本，未命中才批量折叠一次；
- **单飞任务**：同一时刻只有一个折叠任务在飞，5s 轮询与启动预热不会重读同一批日志；
- **启动预热**：账本载入后延迟 1.5s 起跑（让宿主 boot 先稳定），把窗口内全部会话
  一次折完，浮窗首次打开就带名字；
- **首屏等待上限 2.5s**：超时则本次先用截断 ID，折叠任务继续在后台跑完，
  下一轮 5s 轮询即有标题 —— 不拿用户的等待换"完美首帧"；
- **降级链**：缓存 → 内存 `sessions.get`（零成本）→ 截断 ID；**绝不编造名字**，
  折叠失败的会话 title 保持 `null`。

### 12.4 呈现：按参考图的设计路径重做排行

参考图（"工作空间活跃分布"）给出的设计路径是**密集排行**：
`名称 | 数值 | 占比·会话数 | 行内迷你分布条`，配 维度/排序键/搜索/条数 四组控件。
据此把原「会话用量 Top N」升级为「会话活跃分布」：

- **名称列两行**：标题（13px）+ 身份行（11px）= `工作目录 · 最后活跃日`，
  子会话另起标签。标题取不到时退回截断 ID，身份行补上 ID，避免整行无信息；
  hover 提示给全量：标题 / 完整 sessionId / 完整 cwd / 预设名。
- **数值列**：窗口内 tokens 总量（中文大数）。
- **占比列**：`占比% · N 轮消息`；占比分母是**窗口内全部会话合计**（含未列出的
  长尾会话），而非所选行之和 —— 后者会让长尾不在分母里、占比整体虚高。
- **行内分布条**：近 30 日逐日一格（6×16px、2px 间距），空日极淡底、有量按
  **该行自身峰值** 4 档提亮。按行内峰值而非全局峰值归一化是刻意的：分布条回答
  "这行哪几天在活跃"，跨行量级已由数值列表达；按全局归一化会让小行整条褪成底色、
  形态不可读。
- **四组控件**：维度（按会话 / 按工作目录）、排序键（按 Token / 按轮消息）、
  搜索（匹配标题 / ID / 工作目录）、条数（Top 10/20/30/50）。
  全部在**本地集合**上即时生效。

#### 12.4.1 为什么必须有「按工作目录」这一维（实测驱动，非照抄参考图）

第一版只做了「近 30 日 × 按会话」的分布条，**真实账本回放直接证伪**：

| 维度 | 格填充率 | 单行最多活跃天 | 条带形态 |
|---|---|---|---|
| 按会话（45 行） | **4%**（50/1350） | 2 天 | `........................##....` |
| 按工作目录（4 行） | **18%**（21/120） | 6 天 | `........................######` |

单会话的时间跨度**天生很短**——一个会话通常只在当天（或连着两天）活跃，逐日分布
按会话看几乎全是空格，比原来的比例条更没信息。参考图用"按工作空间"做聚合正是这个
原因：同一目录下的多个会话叠加后才看得出"这个项目哪几天在烧 token"。
故补上目录维度（`cwdRanking`）：

- 入参是**全量**会话行（不是截断后的 Top 50），否则聚合结果会随截断口径漂移；
- 依赖折叠所得的 `cwd`；未解析出目录的会话不参与，计入 `unresolved` 由客户端
  如实提示（**不塞进"未知目录"这种假分组**，也不编造目录名）；
- 目录行的身份行是 `N 个会话 · 最后活跃日`，hover 给完整路径；
- 目录维度的占比分母是**已归入目录的合计**（未解析部分不在分母内），与会话维度
  各自独立。

（18% 仍是这个账号的真实活跃度上限：近 30 日里只有 8 天有用量，理论填充上限约 27%。）

### 13.2 span 快照重复回写（账本 19% 纯冗余）

v0.5.0 排查时发现的独立缺陷，**与显示无关但同批修掉**：

`loadLedger()` 载入 `type:'span'` 行时经 `touchSpan` 把这些键重新标脏，而
`process.on('exit')` 的 `flushLedger(true)` 是**强制写**（刻意绕过节流判断），
于是每次 host 正常退出都把全部存量快照重写一遍。

对照实测（真实退出路径，合成账本含 45 个 span 存量）：未修复 **+46 行**
（45 存量重复 + 1 真实推进），修复后 **+1 行**（只有真实推进的会话）—— 修复既消除
冗余，又保持"本次推进必须落盘"的语义。

修复：`touchSpan(date, sessionId, ts, dirty)`，载入路径传 `false`。
存量清理：`plugins/dsh-token-monitor/scripts/dedupe-usage-ledger.mjs`
（无损 min/max 合并 + 写前语义等价校验 + 自动备份），本机 4884 → 3937 行、省 148 KB。

### 13.3 写入节流窗口的取值依据（实测 → **决定：都不动**）

修完"退出重写"后追问：运行期粒度该设多少（`SPAN_FLUSH_MS = 60s`、`flushLedger`
定时器 5s）。实测后**两个都维持现状**，依据如下（本机清理后账本，30 天 / 51 个会话-日）。

**span 快照（`SPAN_FLUSH_MS = 60s`）**

| 指标 | 实测 |
|---|---|
| 体量 | 76 行 / 12 KB —— 占账本体积 **1.1%**（用量行 98.9%） |
| 单行 | 156 B |
| 实际写入间隔（相邻 last 推进） | 最小 **60s**（正好卡阈值）· 中位 **66s** · 90 分位 246s · 最大 581s |
| 典型密度 | 82 分钟跨度的会话只写 9 行；90 分钟 6 行；1370 分钟（≈23h）的会话 44 行（≈ 每 31 分钟一行） |

**一处必须记下的修正**：曾以为"活跃会话每分钟一行"，**那是上界不是实测** —— 它假设
跨度内每分钟都有活动，而 `touchSpan` 只在 `llm/stream` / `tools/result` 触发，真实
会话是间歇性的。中位间隔 66s 说明 60s 节流**几乎不额外触发写盘**（多数推进本就跨过
一分钟）。据此三条不改的理由：

1. 调大只省 <1% 体积（12 KB → 约 3 KB）；
2. 节流窗口不是瓶颈（中位间隔 66s）；
3. 消费端粒度粗 —— 会话行用**日粒度**（身份行"最后活跃日"），唯一用分钟级的是
   「最长聊天时长」卡且取历史最大值；正常退出走 `process.on('exit')` 强制 flush
   **不丢**，60s 只影响崩溃/强杀场景的尾部延长量。

将来若确实要跑长时满负荷会话（极端上界 1440 行/天/会话 ≈ 225 KB/天），**5 分钟**是
合理值：极端上界降到 288 行/天，崩溃最多丢 5 分钟尾部延长。保底机制让长窗口也安全 ——
**新会话的首个快照不受节流**（`written === undefined` 判定立即写，5s 内落盘），
永远不会丢整个会话的跨度。

**用量行（`flushLedger` 定时 5s）—— 账本增长的真正来源**

同批实测：20 分钟账本 +180 行，其中**用量行 +155、span +25**。`flushLedger` 每 5s 把
`pending` 里每个 `(日期, 会话, provider, model)` 键写成一行（只要有新用量就写），
活跃时段约 8 行/分钟 ≈ 0.5 MB/天（按每天活跃 4 小时）。

需留意的上限：`TAIL_BYTES = 8MB` 是启动解析窗口，**账本一旦超过 8MB，启动就会丢掉
更早的历史**（热力图/趋势少数据）。当前 1.0 MB / 30 天尚在安全区，故维持 5s；
若将来逼近 8MB，把 flush 放宽到 30s 可让行数 ÷6（代价：崩溃最多丢 30s 用量）。
