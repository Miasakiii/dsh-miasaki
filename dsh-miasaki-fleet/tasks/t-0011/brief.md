# 任务 t-0011：写入收敛口径的独立复核

## 目标

fleet 刚完成一轮「**写入收敛**」：把「哪些文件经总线唯一入口、哪些刻意豁免」这件事定下来。
本任务是**独立复核** —— 由没有参与该改动的执行者，带着**对抗立场**去找「漏网」与「误豁免」。

## 复核范围（只读，勿修改任何文件）

1. `workers/lib/bus-contract.cjs` 的 `PATCH_PATH_RULES`（可写路径白名单）
2. `workers/dispatch/dispatch-task.ps1` 的 `Write-UsageRow` 与 `Write-BusEvent`
3. `state/graph-events.jsonl`（机器事件流：谁在写、写了什么）
4. `state/tasks.jsonl` 与 `agents/<id>/usage.jsonl` 的**实际**写入者

## 复核问题（逐条回答，不可跳过）

- **Q1** 白名单里每个路径各是什么**性质**（真相 / 派生态 / 归档）？fleet 目录下还有没有
  **该进总线而没进**的真相类文件？（提示：把 `workers/` 与 `state/` 下**会被程序写入**的文件都过一遍）
- **Q2** `status.json` 被**刻意**排除在白名单之外，理由是三条：① 含高频字段（`heartbeat_at` / `tokens`），
  进总线会引发**事件风暴**；② 它的状态迁移**已被事件流完整记录**（`task.started` / `task.completed` /
  `failure.detected`）；③ 强行走总线只会得到「写文件但不产生事件」的**畸形补丁**。
  **这三条是否成立？有没有反例？**（例如：某次状态迁移在事件流里其实没有对应记录）
- **Q3** `Write-UsageRow` 在 applier 失败时**回退直写并告警**（取舍：**数据不丢 > 治理形式**）。
  这个取舍是否自洽？它会留下什么样的**审计缺口**？有没有更好的做法？
