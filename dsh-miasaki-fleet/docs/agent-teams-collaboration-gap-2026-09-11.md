## 0. 摘要（五条）

1. **fleet 不缺基础设施，缺的是把已建好的判定层接进执行层**。G1/G2/G4 判定层与 71 项单测均已落地，
   但派单器 `dispatch-task.ps1` 至今没有任何依赖判定代码，且真实台账无 `graph` 字段、无 `result.json`。
   → 文章一 §3「缺评估体系就别自进化」在 fleet 的对应物不是「补评估」，而是**接线**。
2. **文章二的核心诊断与 fleet 的架构选择完全同构**：「通信通道有了，但协作语义没有」。
   fleet 是**有意**禁止横向通信的（§1.5 最小可见性 + 图工程 §7 不做清单），这是设计决策，不是缺口。
3. **文章二提供的唯一零冲突吸收点是 §7.3「讨论 → 共识 → 执行」**，映到 fleet 即
   **派单前可行性预检**（本轮已据此解决 24 天积压，见 §5）。
4. **文章里的多数「团队机制」与 fleet 的边界清单正面冲突**：岗位体系、协商式 OKR、横向通信、
   结构自演化——fleet 已逐一否决且各有文献依据（见 §6「已否决清单」）。
5. **两篇都未覆盖 fleet 的两个真实缺口**：任务级成本上限、worker 调度级生命周期（超时/orphan 回收）。
   这两条是文章结论落地的前置条件，见 §4。

### 2.2 一处零冲突吸收点 ★

**文章 §7.3「讨论 → 共识 → 执行」三步协议** → fleet 映为**派单前可行性预检**：

```
派单前 ──▶ agent-pick --need <task.requires>
          ├─ 有候选 → 派单（降级候选须带 quality_delta 声明）
          └─ 无候选 → 不派单，标 blocked + blockers[]（复用 G4 契约已有语义）
```

**字段格式契约**（派单器 `dispatch-task.ps1` 与 brief 之间的唯一约定，2026-09-11 定）：

```markdown
## 约束
- 需求能力：requires: coding, analysis       ← 英文 requires: 或中文 需要能力：均可
- ⚠️ 值必须用**档案已声明**的能力名（如 `coding`/`analysis`），否则闸门会正确地拒绝——
  例如给 claude 写 `zh-report` 会失败，因为 `agents/claude/manifest.json` 的 skills **未声明**该能力
  （尽管 t-0006 实测它交付过中文报告）。这类「实测有能力、档案未声明」的缺口，
  应走 G2 的 confidence 回填 + Operator 确认来补，而不是在 brief 里硬写
```

- 解析位置：brief.md 中 `requires:` / `需要能力：` 开头的行（中英文冒号均可）
- 值以逗号分隔，接受能力别名（经 `capability-graph.cjs` 词表规范化）
- **未声明或为占位符（如 `requires: (待补)`）时跳过闸门** —— 这是对存量任务的零行为变更保证
- 显式覆盖：`dispatch-task.ps1 -Requires <caps>` 优先于 brief

- **为什么这是唯一零冲突点**：它不要求 Worker 通信、不引入角色层级、不需要新机制——
  只是把 **Commander 已经能查询的判定**变成**派单前必过的闸门**。
- **实证价值**：t-0003 / t-0004 因此积压 24 天（见 §5）。

## 4. 两篇都未覆盖、但 fleet 真实存在的两个缺口 ⚠️

这两条是本轮源码勘察的独立发现，是文章结论落地的**前置条件**。

### ① 无任务级成本上限

`Test-Budget`（`dispatch-task.ps1` L47–61）只检查「**当日已花** ≥ `budget_per_day` 则拒绝」，
**不预估本次将花多少**；且：
- `manifest.limits.max_tokens_per_task` / `max_concurrent_tasks` **全代码库无消费点**（本轮 grep 实证）
- `timeout_ms` 唯一提及的消费点是「面板告警」，而面板（M2）未落地 → **当前零消费**
- brief 里的「预算：N tokens / 超时：M 分钟」是**文字约束**，无执行点

**风险**：一个失控 worker 可在同步阻塞执行中把当日预算一次性烧穿，且无并发上限。
（Anthropic 实测协作组 token 是独立组 4 倍——成本纪律是 fleet 相对优势，不该在这里漏掉。）

**处置**：任务书加 `limits: { max_cost, deadline }` 并让派单器消费；顺带激活三个悬空字段。

### ② Worker 调度级生命周期为零

- `dispatch-task.ps1` L223 用 `& $exe @args` **同步阻塞、无超时** → worker 挂死则 Commander 会话永久阻塞
- README 自陈：「worker 的调度级生命周期（超时 / 重试 / orphan 回收）**尚无自动化覆盖**」
- 「orphan / 孤儿」在两份设计文档中**零出现**
- 设计中的超时只是「面板红色告警 → 总指挥介入」（**人肉机制**，且面板未落地）

**处置**：派单器加 `-TimeoutMs` + 超时 kill + 一次重试；失败写 `status: error` + `blockers[]`。

## 5. 已执行：t-0003 / t-0004 解积压（2026-09-11）

   —— 该路径指向已归档目录，Worker 依约「只写自己的目录」时将无从交付

**处置**（走 G0 唯一写入入口，两条 `reassign` 补丁）：
- t-0003 → `claude`；t-0004 → `claude`
- 依据：`claude` 提供 `cap:coding`，且 **t-0006 有实测证据**（exit 0、中文报告、验收 3/3）
  —— 用**真实任务证据**而非档案声明（这正是 G2 设计里 confidence 回填的用途）
- 两份 brief 的交付物路径同步改为 `agents/claude/notes.md`，并追加「改派记录」段
- t-0004 brief 补注**源文档时效警告**（`collective-memory.md` 停留建库期，含已废弃的 dsh-sdk 路线）

**未做的事（有意）**：
- ❌ **未扩充任何能力声明**——不为单个任务伪造 `zh-report` 能力。
  能力回填应走「真实任务证据 → Operator 确认」（G2 别名表「保守且可审计」纪律）

**副产品**：**G0 唯一写入入口首次在真实数据上被使用**——总线版本 `0 → 1 → 2`，
`state/graph-events.jsonl` 首次生成（此前不存在）。这同时兑现了图工程 §8 的待办
「G0：跑真实任务产出机器事件」。
