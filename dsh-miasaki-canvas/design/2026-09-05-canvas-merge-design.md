## 1. 背景与目标

线性对话的局限：一个问题产生多个值得探索的方向时，只能选一条深入，其余被淹没在对话记录里；两条探索线之间无法重新汇合。DSH 原生只提供 fork（单亲树），没有 merge。

**目标**：在 dsh-synapse 的画布基础上增加**会话合并**能力（分支已由它解决），并配套画布交互增强。合并产生**真实 DSH 会话产物**——可继续追问、可再分支、可再合并。

**非目标（首版不做）**：多人协作空间、独立桌面应用、多 Agent 编排（fleet 线职责）、跨 workspace 合并、直接让模型读取画布空间状态。

## 3. 边界红线（继承 dsh-synapse，永不越界）

1. **DSH session log 是唯一事实来源**：插件只投影已提交事件，不制造第二套会话历史。
2. **不修改**：系统提示、模型请求、工具 schema、provider 路由、KV-cache 前缀、审批上下文。
3. **画布元数据独立存储**（`$DSH_HOME/synapse/workspaces.json` 或自定路径）：删除只丢布局/血缘展示，不丢 DSH 会话。
4. **合并 = 构造 user 消息 + DSH 原生 fork**：插件不直接调模型。模型综合由 DSH 正常对话完成。
5. 只支持 web profile（沿用 dsh-synapse 的 patch 机制）。

## 5. 核心设计：合并的三层分离

DSH 原生 session 只有单亲 fork（`header.parentSession` + `seedLength`），没有 merge。合并必须三层分离：

| 层 | 归属 | 合并如何落地 |
|---|---|---|
| **L0 事实层**（DSH session log） | DSH | 从一条线 fork 出新会话，首条消息注入另一条线的内容 + 用户意图，DSH 正常生成「合并产物」。原生血缘仍是单亲（fork 自 A），不动 DSH 边界 |
| **L1 投影层**（画布元数据） | 我们 | thread 新增 `mergeFrom` 元数据 → 菱形合并节点 + 双亲连线（DAG 渲染） |
| **L2 交互层**（画布 UX） | 我们 | 选线 → 合并请求卡预览 → 执行 → 菱形节点展示双亲血缘 |

### 5.1 合并元数据（L1）

```jsonc
// thread 新增字段（schema v4 → v5 迁移）
{
  "mergeFrom": null | {
    "sources": ["threadA", "threadB"],   // 两条来源线的 threadId
    "forkSource": "threadA",             // 从哪条线 fork（继承其模型/工具/cwd）
    "anchorSeqA": 12,                    // A 线锚点卡的 seed 边界
    "anchorSeqB": 7,                     // B 线锚点卡
    "injectedForm": "full",              // full | summary | manual
    "userIntent": "综合两条线的方案…"     // 用户自定义合并指令（可空）
  }
}
```

- `sources` 是画布血缘（DAG），`forkSource` 决定 DSH 原生血缘（单亲）。
- 迁移：load 时 v4 → v5 补默认字段，参照 dsh-synapse 现有迁移机制。

### 5.2 合并执行流（L0）

```
用户选 A、B 两条线的锚点卡（或拖拽并置手势触发）
  → 合并请求卡（菱形 draft）预览：fork 源线 / 注入形式 / 自定义指令
  → 确认执行：
      a. DSH 原生 fork：从 forkSource 线锚点卡的 seed 边界切出新 session
      b. 首条 user 消息 = 结构化合并请求：
         [合并请求]
         来源线 A（fork 自）：<锚点卡问题 + 最终回答/摘要>
         来源线 B：<全文引用或摘要>
         用户意图：<自定义指令，可空>
         请综合两条线的结论……
      c. DSH 正常生成回复
  → 投影回画布：新 session 长成菱形合并卡（mergeFrom 记录双亲）
```

状态机：`draft`（预览编辑中）→ `pending`（已提交，等待 fork + 首条回复）→ `committed`（投影回画布）／`failed`（可重试）。

### 5.3 注入形式权衡

| 形式 | 优点 | 代价 |
|---|---|---|
| `full` 全文引用 | 精确、无信息损失 | 上下文开销大（需截断策略） |
| `summary` 指令式提炼 | 省上下文 | 多一轮 token、有信息损失 |
| `manual` 用户手选 | 用户掌控 | 操作负担 |

MVP 默认 `full`（注入锚点卡的投影内容，8000 字符上限天然兜底）+ 可选自定义指令；`summary` 进 M4。

### 5.4 可逆性

- draft 可随时取消；
- committed 合并卡可归档：移除画布血缘展示（`mergeFrom` 置空或线程归档），DSH 会话保留，由用户决定是否手动删除；
- 合并是**衍生**不是**销毁**：原两条线默认保留。

### 5.5 多代合并血缘（再合并，已决议：D 方案 + 吸收态标记）

场景：A⊕B → M1，M1 线续追问出新卡 M1'，M1' 再与 C 合并 → M2。M2 的入边如何渲染？

关键事实：

- **DSH 内容继承是单线**：M2 的 fork 链 = M2 ← M1' ← M1 ← A；M1 历史中的合并请求消息已含 A、B 的引用文本——内容传递包含，但那是「引用文本」不是「血缘」。
- **画布血缘是 DAG**：`mergeFrom.sources` 记录的是**两条线的锚点卡**（threadId），不是叶子祖先。
- 合并单位是**线**不是卡：用户选线的末端锚点卡，线的祖先沿 `parentId` / `mergeFrom` 链回溯。

方案对比：

| 方案 | M2 的入边渲染 | 优点 | 缺点 |
|---|---|---|---|
| A 只连直接来源 | M2 → M1'、C | 局部清晰、边数可控 | 「M2 综合了什么」需逐层回溯 |
| B 传递展开 | M2 → A、B、C（全部叶子祖先） | 一眼看全构成 | 多代后边数爆炸、画布杂乱 |
| C 折叠吸收 | 中间合并节点半透明/虚线，入边重指向叶子 | 全貌且边数不涨 | 视觉语义复杂、易误解 |
| **D 混合（已采纳）** | 默认方案 A；详情面板提供「传递血缘」视图（可展开祖先 DAG） | 两者兼得 | 多实现一个面板视图 |

**决议：D 方案**。默认画布只连直接来源锚点（分层 DAG、可读）；菱形详情面板提供「传递血缘」视图，按需展开全部构成叶子与中间合并链（与 git 的 `log --graph` 默认直连父子 + 图形化工具按需看全貌同构）。

**吸收态标记（已决议：要）**：

- 当 M1 线的产物被后续合并 M2 吸收（M2 的 `sources` 锚点卡沿 `parentId`/`mergeFrom` 链回溯命中 M1），M1 卡显示弱化小标记「已被 M2 吸收」（虚点或小徽标）。
- 标记**不改变 M1 的可用性**：M1 仍是活会话，可点击、可追问、可再分支；点击标记可跳转 M2。
- 实现：合并执行时写入反向索引 `absorbedBy`（threadId → 吸收它的 merge 节点 threadId 列表）；归档/撤销合并时同步移除；投影时据此渲染标记。

## 6. 画布交互增强（L2，吸收 Huabu 理念）

1. **多选/框选卡片**：矩形框选或 Ctrl 点选，选中态高亮。
2. **拖拽并置 = 合并手势**：A 卡拖到 B 卡近旁（碰撞检测）→ 弹出「合并这两条线？」气泡 → 进入合并请求卡。空间操作即意图表达（Huabu「思考外化」在会话层的落地）。
3. **合并请求卡**：菱形 draft，画布上实体化、可编辑（fork 源线切换、注入形式、指令文本框），确认后进入 pending。对应 Huabu「人在回路」。
4. **DAG 渲染**：fork 保持单亲连线，merge 节点菱形 + 双亲入边；连线语言从树升级为 DAG。
5. **空间语义翻译层**：把画布关系（选中顺序、并置、连线）转成合并请求消息的结构化字段——因为插件**不能让模型直接读画布状态**，空间语义只能「翻译」进 user 消息。

## 7. 架构

### 7.1 二开方式

| 方案 | 评估 |
|---|---|
| 甲：fork dsh-synapse 改名，直接在其上开发 | **首选**。MIT 协议；复用投影/画布/同步全部实现，只加 merge 能力 |
| 乙：独立插件依赖其投影库 | 不可行：它未暴露库 API，只有插件入口 |
| 丙：cordis patch 叠加覆盖 synapse 行 | 只适合配置级覆盖，加功能不可行 |

结论：方案甲。需与上游保持跟进（其版本更新含修复）。

### 7.2 模块划分

- **Host（index.js）**：`WorkspaceStore` v5（merge 元数据 + 迁移）、`/synapse` 端点新增 merge RPC（fork + 注入首条消息）、并发写串行化（沿用现有 serial + 锁）。
- **Client（client.js / app.js）**：多选/框选、拖拽并置手势、合并请求卡、菱形 DAG 渲染；沿用视口虚拟化与流式补丁。
- **cordis.patch.yml**：注入 profile 行（沿用现有机制）。

### 7.3 关键 SPIKE 点（M1 内验证）

- DSH sessions 服务的 fork API 形态与 seed 边界语义（从 dsh-synapse 的 bridge 代码直接抄）。
- 注入首条消息走哪个 sessions bridge API。
- 本机 `dsh plugin --profile web add link:<路径>` 的本地开发安装闭环（dsh-synapse 文档已给出命令，需实跑验证）。
- fork 后新 session 的首条消息如何携带（用户消息长度上限、是否需要等待 session 建立后再发）。

## 9. 风险

- DSH 升级破坏 bridge API（对策：SPIKE 先行、跟上游节奏）。
- 注入内容爆炸（对策：投影 8000 字符上限 + summary 形式 + 截断标记）。
- 双线深分歧无机械合并算法（对策：明确「综合靠模型 + 人」，不承诺自动冲突解决）。
- 与上游 dsh-synapse 分叉维护（对策：定期合并上游更新，merge 功能独立成模块便于 rebase）。
